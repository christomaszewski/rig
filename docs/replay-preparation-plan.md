# Replay preparation implementation plan

Historical checkpoint: the validation below applies to 2026-10-20. Later AMD64/ARM64 and
combined camera/bag acceptance is in the
[v0.2.72 readiness report](releases/coordinated-replay-readiness-2026-10-27.md).
Current version-1 and shared version-2 recipe behavior is documented in [REPLAY.md](REPLAY.md).

Status: implemented, 2026-10-20. Scope: Rig, the ros2-bag-player in rig-infra,
and camera-service input mounting. This document preserves the agreed design and acceptance
criteria; [REPLAY.md](REPLAY.md) describes the implemented workflow. Suite packaging stays deferred.

Validation: all 63 Rig test scripts, the player host suite, and the camera input-environment
tests pass. Real Linux ARM64 container tests cover MCAP/SQLite reindexing, a new remapped
subscriber, windowed playback, remapped latch restoration, and clock-only playback. An isolated
macOS Docker CLI exercise wires a missing player, prepares a metadata-free bag without changing
the original, replays it, and seals the new run through auto-end. Actual AMD64 container execution
and end-to-end camera video decoding have not been exercised here; camera selection/copying and
mount arguments have host regression coverage.

Make a hand-built deployment replay a specified current or legacy recording without reconstructing the original deployment. Add instance-level `replay.start`, a shared replay planner, and `rig replay check` / `rig replay prepare`. Use broad topic playback with output exclusions; require neither publisher/subscriber declarations in service riggings nor live graph discovery.

Keep recipes portable enough to package with a suite's vehicle plan later. Registry publication and recipe installation are deferred; local recipes and preparation must work independently of a registry.

## 1 Decisions and boundaries

- `vehicle.yaml` owns persistent startup choices. An optional row-level `replay: {start: true|false}` controls participation in replay independently of ordinary `up`.
- A recipe owns source-specific choices: bag session, recording-to-instance bindings, topic exclusions/remaps, and optional playback settings.
- Broad playback is the default: play recorded data topics unless explicitly excluded or identified as outputs regenerated by selected instances. Do not require an input allow-list.
- Recorded graph epochs are optional evidence for output ownership. They are not a requirement for a new consumer to receive data.
- Unknown current outputs remain unknown. Report the limits of namespace and historical ownership evidence; preparation must not claim to prove collision-free playback.
- Check, prepare, dry-run, and execution share one resolved plan. Preparation starts no deployment stacks.
- Preserve the source recording. Adapt legacy layouts and rebuild indexes in derived storage, with provenance.
- Do not invent graph observations, missing service requests, original image digests, capture timestamps, or historical deployment identity.
- Keep the existing `rig reconstruct` and explicit `rig run retrofit` workflows. Preparation reuses their helpers where appropriate but does not inherit retrofit's move-by-default behavior.

Deferred: live subscription discovery, mandatory `interface:` declarations, static analysis of service code, automatic semantic topic matching, filtering individual TF/diagnostic messages, ROS 1 conversion, cross-distro message-schema conversion, simultaneous playback of multiple bag sessions, and a new producer-readiness synchronization protocol.

## 2 Baseline before implementation

| Area | Current behavior | Required change |
| --- | --- | --- |
| Startup policy | `replay.startup_selection()` returns omissions. Top-level `replay.services` / `replay.instances` can suppress startup, but `start: true` does not positively select an ordinary autonomy instance. | Return complete selections and reasons, including positive inclusions. |
| Instance model | `manifest.Sensor` and `_parse_entries()` have no replay setting. | Preserve a tri-state instance setting: absent, true, false. |
| Topic selection | Named instances use source-graph subscriptions; no-name replay uses bag topics minus historical publishers. | Make broad playback available consistently, including named/new instances. Preserve recorded-input mode explicitly. |
| Session handling | Rig scans metadata across sessions for topics and timing; the player selects one configured logger/session, normally `latest`. | Resolve exactly one bag session before selection, windows, camera alignment, or service-event checks. |
| Loading | `cli._load()` normally materializes configs and can fail before producing a readiness report. | Add a read-only planning path with in-memory config resolution and structured issues. |
| Legacy helpers | `reconstruct.py` can wire a player, attach a matching artifact, and adopt external camera recordings. Adoption moves data by default and selects sessions by their start time. | Extract reusable inspection/selection operations and add source-preserving preparation. |
| Player | `play_cmd.py` accepts fixed selection and session settings; its strict schema has no remap field. | Add a tested plan handoff and remapping across normal playback and helper publishers. |
| Round trips | Bake reconstructs instance rows; planned suite installation copies selected row fields. Neither currently preserves a new row replay field. | Cover manifest edits, bake/capture, promotion, installation, reconstruction, and replay build scope. |

## 3 Instance startup semantics

```yaml
infra:
  - name: radio
    service: doodle
    config: config/infra/radio.yaml
    replay: {start: false}

autonomy:
  - name: new_planner
    service: planner
    config: config/autonomy/new_planner.yaml
    enabled: false
    replay: {start: true}
```

`new_planner` starts during replay even though normal `up` omits it. `radio` does not start during replay, but its recorded topics remain eligible.

| Setting | Replay meaning |
| --- | --- |
| Absent | Preserve automatic selection: enabled infrastructure, detected recording sources, and an automatically managed player when needed. |
| `start: true` | Positively include the instance, regardless of its tier or normal `enabled` flag. |
| `start: false` | Omit the instance process, including automatic recording-source startup; preserve eligible bag data. |

Resolve precedence in this order:

1. Explicit CLI selections: positional instance names, `--live`, and `--include-service`. A simultaneous explicit skip/include is an error.
2. Effective instance policy. Row `replay.start` and deployment `replay.instances.NAME.start` are two spellings of the same setting; contradictory values in the same deployment are errors. Existing local-file instance overrides take precedence.
3. Effective `replay.services.SERVICE.start`, retaining existing local-file merge order.
4. Descriptor startup eligibility and automatic selection. Existing descriptor `replay.start: false` suppresses automatic startup; an absent/default-true descriptor does not cause every service to start.

Preserve instance specificity: a service-level local override does not erase an explicit instance-level choice. Keep `--skip-service` / `--skip-instance` as stronger, separate operations that omit startup and associated bag data. When source ownership cannot be established, report what those skips can and cannot identify.

The player stays managed by Rig; reject attempts to disable it through startup policy. Required router/transport infrastructure omitted by policy produces an actionable preflight issue rather than a silent policy override.

A selected recording-capable instance with usable recordings runs from those recordings. `--live` continues to opt into actual hardware. A newly forced `start: true` source with missing recordings must not silently become a hardware session: report the missing mapping and require an explicit live choice.

Implement a shared selection result containing each instance's role (`infra`, `consumer`, `recording-source`, `live-device`, or `player`), inclusion reason, data binding, and ordering. Use it for preflight, image validation, startup, snapshots, teardown, and reports. Consumers selected through policy must receive the same clock checks as positional consumers.

For build planning, reuse policy resolution without requiring a run. Include explicit replay-only instances even when disabled for ordinary deployment; include potentially automatic recording sources conservatively. Keep source-dependent launch selection separate from this build-time superset.

## 4 Commands

All commands run against the current deployment unless `--root` selects another.

```sh
rig replay check RUN
rig replay prepare RUN --recipe field-test
rig replay check --recipe field-test
rig replay --recipe field-test

# Preview preparation writes and legacy processing.
rig replay prepare RUN --recipe field-test --dry-run

# Supply a known player package or checkout when none is configured.
rig replay prepare RUN --recipe field-test --player PATH_OR_PINNED_REF
```

Preserve `rig replay RUN [INSTANCE ...]` and `rig run replay ...`. Add equivalent `rig run replay check/prepare` spellings. An explicit `--recipe` selects `replay/NAME.yaml` or an explicitly supplied recipe path. `prepare RUN` without a recipe name creates a deterministic, filesystem-safe name and prints the exact follow-up command; handle duplicate run IDs without overwriting an unrelated recipe.

`RUN` overrides the recipe's default source for that invocation and is recorded as a local binding. Omitting both is an error. Resolve a source label to a concrete run before preparing; never replay a different “newest” run silently from an existing plan. Do not silently discover or activate arbitrary recipe files for plain `rig replay RUN`; that command can still execute an ephemeral plan.

Handle command ambiguity explicitly: preserve a run literally named `check` or `prepare` through `rig replay -- RUN`. Cover grouped translation, global `--root`, help, and completion rather than adding an incompatible second parser path.

### Check

Read the deployment, recipe, and source inventory; resolve the plan and print:

- Selected/omitted instances, execution modes, and reasons.
- Exact bag session, timing bounds, separate recording sessions, and source mappings.
- Played, excluded, remapped, and uncertain topics, with the reason for each exclusion.
- Missing player/transport support, selected image/runtime/CPU compatibility, output storage, and source mount reachability.
- Legacy repairs needed, unresolved choices, warnings, and the next concrete command.

Do not write configs, create runs, move files, repair indexes, pull/build images, or start containers. A missing player must still permit useful source inspection. Expected missing inputs should produce aggregated issues instead of an early traceback.

Use bounded read-only host/image inspections where available. Distinguish `ok`, `warning`, `error`, and `not_checked`; expose `ready_to_prepare` and `ready_to_run` separately. Required unavailable checks prevent a green run-readiness result. Optional limitations remain warnings. Add `--format json`; use exit 0 for run-ready, 1 for blocked/incomplete readiness, and 2 for invalid arguments.

Without service interface declarations, check cannot prove that every consumer has an input or that recorded type definitions match every new subscriber. State that scope in the report. Type names and available type-support checks are useful evidence, not a wire-compatibility proof.

### Prepare

Use the same plan to perform only identified preparation work:

- Create an initial recipe or read an existing one; preserve user edits on repeat runs.
- Wire a missing player using the specified checkout/pin or an already resolved deployment service. Do not choose an arbitrary latest package or replace existing service pins.
- Build a derived source layout and indexes when required.
- Write resolved configuration, a preparation report, local source bindings, and provenance.
- Re-run applicable checks and print the recipe-based replay command.

Preparation may run a bounded one-shot storage inspection/reindex helper when needed. It must not start routers, consumers, recorders, or the replay session. Report missing helper images with a pull/build action rather than hiding downloads or builds inside preparation.

Stage writes and publish them atomically. A failed repair must not leave a ready plan. Roll back player wiring if the corresponding preparation transaction fails. Detect concurrent preparation for the same output. Support `--dry-run` through the same mutation plan with no writes or helper execution.

Repeated preparation is idempotent. Regenerate disposable state when inputs change, retaining explicit recipe decisions; do not overwrite a recipe with a newly inferred one.

### Execute

Use the shared plan for direct and recipe-based replay. Revalidate input fingerprints and host-dependent checks immediately before starting stacks. Recompute harmless disposable state; stop with `prepare` instructions when renewed normalization, indexing, or unresolved choices are required.

Retain the clean-host guard and existing explicit force semantics at execution. Check and prepare can inspect a busy destination without stopping its stacks, but must report that execution is currently blocked. A known open source run is not eligible for preparation or replay. Missing legacy seal metadata is a separately reported uncertainty; verify that source inventories remain stable during preparation and never create a historical seal as a side effect.

Keep existing windows, `--calls`, `--export-calls`, `--wall-clock`, `--live`, skip/include flags, and auto-end behavior. Each accepted option must affect check, prepare, and execution consistently. Auto-end remains unsupported without a bag player; report this during planning.

Broad playback becomes the default for named and unnamed instances. Provide `--selection recorded` for the previous source-subscription selector and document the default behavior change. Explicit recorded mode may warn about unavailable source graph evidence; absence of epochs is not an error in broad mode.

## 5 Recipe and generated state

```text
deployment/
  vehicle.yaml
  services.yaml
  replay/
    field-test.yaml
  var/replay/field-test/
    bindings.yaml
    <source-key>/
      resolved.yaml
      report.yaml
      provenance.yaml
      config/
      source/                 # only when adaptation is required
```

Recipes are editable and versionable. `var/` is already ignored. Use a source key that distinguishes duplicate run IDs and different source inventories; keep host paths out of portable recipe identity. `bindings.yaml` records the local source locator and active prepared generation. Generated files are never executable recipes or registry payloads.

Proposed version-1 recipe:

```yaml
version: 1
source: 20260827T100000Z_field     # optional default; RUN can supply the source

bag:
  logger: bag_logger
  session: latest                # resolved to an exact session during preparation

# Historical ownership aliases; no automatic renaming of ROS topics.
instances:
  new_planner:
    recorded_as: planner
  cam_front:
    recorded_as: front_camera

# Overrides for recording discovery, including external legacy directories.
recordings:
  cam_front:
    from: recordings/front_camera
    sessions: [cam-20260827T100000Z]

playback:
  topics: all                   # alternatively an explicit list of recorded names
  exclude: [/planner/trajectory]
  keep: [/tf, /tf_static]        # retain these despite an inferred exclusion
  remap:
    /old_gnss/fix: /gnss_primary/fix
```

`recorded_as` provides a source instance identity for ownership lookup and default recording discovery. It neither changes the destination instance identity nor implicitly remaps topics. `recordings.from` overrides discovery only; relative paths are relative to the source run, and absolute paths are explicit external imports. Recipe-relative auxiliary files, such as a call script, resolve relative to the recipe directory. Define these path bases once and validate them.

Use exact topic names for `exclude`, `keep`, and remap keys in version 1. Reject contradictory keep/exclude entries; do not introduce ambiguous pattern precedence. Missing explicit topic names produce diagnostics instead of quietly ineffective settings. Add explicit `playback.services` or a recipe-relative `playback.calls` when service calls are requested; they remain mutually exclusive.

Validate unknown fields, booleans, version, instance names, path containment, and remap collisions. Persist normalized values and reasons in the resolved plan. CLI playback overrides have highest precedence for the current invocation and are captured in execution provenance.

Fingerprints cover the recipe, effective deployment config including local/env contributions, selected descriptors/launch surfaces and lock/image identity, bag metadata and file inventory, recording sidecars, call scripts, and selected sessions. Hash small control files; use an explicitly documented size/mtime inventory for large media by default. Do not call this a cryptographic verification of recording bytes.

The resolved plan must contain concrete session IDs, absolute execution paths, final topic selection, preparation actions, selected images, and limitations. A wall-clock release timestamp is execution-only state: calculate it after preparation and image checks, never save a future start time for later reuse.

## 6 Topic selection without interface declarations

Read the selected bag session's index to obtain recorded topic names, types, counts, timing, and available QoS metadata. The plan starts with all recorded data topics or the recipe's explicit list.

Apply the following rules deterministically:

1. Exclude ROS plumbing and `/_service_event` channels from ordinary data playback. Rig owns `/clock`; do not replay a recorded clock alongside the player's generated clock.
2. Apply explicit user exclusions and existing skip-data policies in the original recorded-name space.
3. Use optional source graph ownership to identify topics exclusively produced by instances now regenerated live, accounting for `recorded_as`. Exclude those unless explicitly kept.
4. When graph evidence is missing, use the existing namespace convention as a labeled heuristic for mapped/replayed producers. Do not prune an unknown new consumer's entire namespace merely because it starts; its inputs may also be namespaced there.
5. Retain shared topics such as `/tf`, `/tf_static`, and `/diagnostics` unless explicitly excluded. A topic with multiple historical producers must not be dropped just because one producer runs now. Report possible mixed live/recorded contributions.
6. Apply exact remaps to the surviving stream. Validate destination-name/type conflicts, multiple recorded topics mapped to the same destination, and mapped destinations known to be regenerated. Report concrete conflicts for resolution.

Historical ownership is not proof of current output behavior after code/config changes. Record its use as an inference. Newly added services with unknown outputs get a focused warning; they do not need a rigging declaration to run. Explicit `exclude`/`keep` entries resolve individual cases without creating a fleet-wide interface-maintenance requirement.

Do not silently fall back to an empty allow-list that the player interprets as “all.” If selection is empty, distinguish sources-only replay, intentionally clock-only playback, and no useful inputs. Preserve a player when a selected simulation-time workload needs its clock even if no bag data topics remain; make this an explicit player capability.

Service calls require separate selection. Broad data playback must not reissue every recorded request. Use an explicit service list or call script in the new workflow; keep existing graph-derived selection only in explicit recorded mode. Renamed service endpoints require an explicit supported mapping or an edited call script, not name guessing.

Apply topic remaps consistently to bag playback and latch restoration. A windowed replay must not publish a remapped live stream while restoring its pre-window state under the old names. Specify service remaps separately if added later.

## 7 Exact source and session resolution

Introduce a source inventory before service selection: source kind, original identity, concrete bag sessions, recording sessions, optional epochs, and provenance availability.

Choose a logger/session from the recipe or current player configuration. Resolve `latest` once; persist the exact selection, inventory fingerprint, start time, and duration. Multiple unexplained logger choices require a selection. A bag split into several files remains one session.

Use this same session for topic inventory, window bounds, service-event availability, latch restoration, call-script zero, and camera alignment. Do not union topics from one session while playing another, or align cameras to the earliest bag in an unrelated session.

Retain the existing camera `--session` meaning and add distinct bag-selection options if needed; do not repurpose one flag for both. Recording sessions must be explicit or selected by supported timing evidence. Prefer interval overlap when start/end times are known; do not assume “started inside the run” captures every overlapping legacy session.

A source missing timestamps may still permit a limited sources-only playback mode. Report which alignment/window features are unavailable; refuse a request that requires timing that cannot be recovered. Do not derive capture time from file modification time.

## 8 Legacy source support

Support these cases in the first implementation:

| Source condition | Preparation action |
| --- | --- |
| Current canonical run | Use directly where mappings/mounts permit; no normalization required. |
| Run without capture, lock, or historical configs | Use the destination deployment. Mark historical provenance unavailable; no retrofit artifact prerequisite. |
| Run without graph epochs | Use broad playback plus explicit settings and labeled ownership heuristics. |
| Canonical bags without usable metadata | Recover an index in derived storage using a compatible storage helper; validate the result before using it. |
| Standalone ROS 2 bag directory or explicitly identified bag file | Create a derived run layout and manifest describing the import. Preserve the original path/identity; do not claim it was a native Rig run. |
| Camera sidecars/video outside a run, or under old instance names | Bind explicit source directories to destination instances, validate sidecar/segment completeness, select sessions, and materialize the expected layout. |
| Legacy deployment/launcher cannot consume recordings | Report the required service update or source capability; do not silently swap versions. |
| Missing bytes, unsupported storage/schema, or unrecoverable timing | Report the specific limitation and supported recovery action, if any. |

Reuse camera session inspection from `reconstruct.py`, but split inspection, selection, and materialization so preparation never calls the existing moving adapter accidentally. Preserve `rig run retrofit` behavior for operators who explicitly use it.

Adapters produce a common source inventory plus proposed operations. Initially provide canonical-run, standalone-rosbag2, and camera-sidecar adapters. Storage parsing/reindexing belongs in the ROS-capable helper in rig-infra; Rig itself remains ROS-independent. Probe supported storage operations against the selected image rather than assuming all `.mcap` and `.db3` variants are repairable.

Materialize derivatives with copy-on-write clones or safe read-only hardlinked payloads where suitable, copying files that repair tools could modify. Never repair or rewrite a hardlink shared with the original. Check disk space before large copies and identify partial outputs as incomplete until validation and atomic publication succeed.

Do not rely on symlinks whose targets are outside container mounts. Mount the actual prepared input root read-only in the player and every recording source. Audit camera-service's input-mount handling for arbitrary `var/replay/.../source` paths outside `RIG_DATA_DIR`; add the needed mount behavior and tests rather than assuming host-readable paths are container-readable.

Derived provenance records original locators, selected input files/sessions, transformation/helper versions, operations, recovered fields, unresolved fields, and fingerprints. Keep original and derived IDs distinct. An imported manifest's creation timestamp must not masquerade as the historical recording start or seal time.

## 9 Shared implementation structure

Extract orchestration from the existing monolithic `replay.cmd()` behind small modules:

| Module or area | Responsibility |
| --- | --- |
| `replay_recipe.py` | Versioned recipe loading, validation, portable references, local bindings. |
| `replay_sources.py` | Inventory, session selection, adapters, proposed legacy actions. |
| `replay_plan.py` | Pure startup/data/clock planning, issue collection, fingerprints, resolved schema. |
| `replay_prepare.py` | Transactional wiring, materialization, repair execution, generated-state lifecycle. |
| `replay.py` | Existing entry points and execution/teardown using the shared plan. |
| `manifest.py`, `targets.py` | Instance policy representation and consistent runtime/build selection. |
| rig-infra player | Plan capabilities, exact-session playback, storage helper, remaps, latch/clock handling. |
| camera-service | Prepared input mount compatibility where existing behavior is insufficient. |

These are module boundaries, not a requirement for a general plugin framework.

Add a structured, versioned player handoff, provisionally `RIG_REPLAY_PLAN`, alongside the source root. Advertise support through the player's optional launcher capability/inspection verb; do not infer support from a package version string. Preserve legacy env-only invocation for older workflows and reject unsupported prepared-plan features before starting infrastructure.

Register any new Rig-owned environment keys in both ownership validation and set-or-pop cleanup. Validate contradictory plan/env inputs. Keep source paths and generated config paths stable for the session, including container restarts and unrelated `rig status` calls.

Refactor config rendering to support in-memory planning. Do not call normal `_load(render=True)` from a command advertised as read-only. Scope host/runtime checks to selected services while still reporting malformed deployment structure clearly.

At execution, snapshot every launched instance, including replay-only instances with `enabled: false`; the current config collector filters enabled rows. Save the recipe, resolved plan, adapter provenance, actual startup set, selected session, clock/window, call-script digest, and effective image selection in the new replay run. Preserve provenance links to both the original and any derived source.

## 10 Delivery sequence and acceptance

### A Instance startup policy

Implement tri-state row parsing, precedence, positive selection, reasons, and replay build-scope integration. Preserve existing top-level settings and CLI overrides. Carry the field through row edits, bake/capture, reconstruction, and vehicle-plan promotion/installation.

Acceptance: disabled-for-normal-up autonomy starts with replay true; infra and recording sources remain off with replay false; CLI conflicts fail; local precedence works; a missing source cannot silently launch hardware; a promote/install and bake/reconstruct round trip preserves behavior.

### B Planner, recipe, and selected-session inventory

Introduce versioned schemas, in-memory loading, exact bag selection, broad topic planning, and optional historical ownership mappings. Keep execution on the old path until plan parity tests pass.

Acceptance: new and renamed consumers work with no `interface:` declarations and no epochs; a non-latest selected bag controls both topics and timing; source aliases do not silently remap topics; shared topics survive automatic exclusion; unknown outputs are reported.

### C Player contract and prepared-input mounting

Implement capability negotiation, structured plan validation, exact-session selection, remaps across player/latch helpers, explicit service-call behavior, clock-only support, and prepared-source mounting. Add storage inspection/reindex helper support for the first verified legacy formats.

Acceptance: unsupported old launchers fail before stack startup; a remapped window restores latches under the same destination names; no accidental service requests or second clock; camera playback reads a prepared directory outside the normal data root.

### D Check and preparation commands

Add parser/group translation/completions, structured reports, player wiring, transaction handling, and generated-state freshness checks. Connect check, prepare, dry-run, and execution to the shared planner.

Acceptance: checks and dry runs leave the deployment/source unchanged; missing components are reported together; repeated preparation preserves edited recipes; failures leave no ready plan or half-wired player; execution detects stale preparation; duplicate run IDs remain separate.

Also cover busy-destination inspection versus execution, rejection of a known open source, and a source that changes while a repair is being staged.

### E Legacy adapters and provenance

Implement source-preserving standalone-bag normalization, missing-index recovery, and external/renamed camera recording binding. Keep ambiguous mappings explicit and unsupported repairs visible.

Acceptance: canonical legacy run without capture/graph replays; supported standalone bag replays; repair changes only derived files; camera session overlap selection is correct; corrupt/missing sidecars and ambiguous associations produce actionable reports; historical provenance is never fabricated.

### F End-to-end verification and documentation

Update README, runbook, cheatsheet, build/replay guide, command help, and migration notes. Explain broad-playback defaults, output-collision limits, explicit recorded mode, recipe path semantics, and source preservation.

Use the repository's existing plain Python test scripts. Add focused coverage in manifest, replay, targets, CLI groups/completions, bake, reconstruction, and planned installation tests, plus new recipe/planner/preparation tests. Run the complete existing script suite after integration, then the affected rig-infra and camera-service tests.

Run real container acceptance with a small known recording on supported Linux-container amd64 and arm64 hosts, including macOS Docker source-path mounting where available. Cover a new consumer, a renamed consumer, a renamed camera source, a multi-session run, windowed/remapped playback, and a legacy import. A mocked launch test is not evidence of storage-plugin, type-support, or mount compatibility.

## 11 Packaging recipes with suites later

Keep the recipe schema independent of registry APIs. Source bindings are optional/local, instance references are deployment names, and portable auxiliary paths are recipe-relative. Generated plans contain host paths and stay outside distributable payloads.

A future suite can pin services/profiles/overlays plus its vehicle package; that vehicle package can carry recipe files alongside the vehicle plan. Existing overlays remain per-service config deltas. Defer the recipe-payload extension, promotion/install commands, recipe dependency closure, and registry validation until a later change.

For this release, preserve `replay.start` through existing vehicle-package round trips and copy the selected recipe/resolved plan into replay-run provenance. Do not silently discard local recipe files in any newly added replay export path. Extending ordinary artifact/suite packaging to include recipe directories requires an explicit follow-up, with local source paths excluded or rebound.

## 12 Completion criteria

From a manually authored deployment, an operator can select replay participants in `vehicle.yaml`, check a specified run, prepare a named recipe, and replay it without describing every service's publishers/subscribers. The same workflow handles the supported legacy layouts and external recordings while preserving their originals.

The check report, prepared plan, and actual startup agree; every nontrivial inference and unresolved compatibility limitation is visible. Exact bag/session timing and container input access are verified. Registry packaging remains optional and deferred without requiring a redesign of the recipe format.

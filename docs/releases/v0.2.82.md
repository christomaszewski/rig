An image that a build did not change now keeps its published digest, so a repeated `rig build`
leaves the images above an unchanged base cached instead of rebuilding them from scratch.

- A build whose steps are all cached publishes byte-identical per-architecture images under a
  new index digest every time, because the provenance attestation in the index is unique to the
  build. Dependents receive that digest as `RIG_BASE_IMAGE`, and BuildKit keys every step of a
  Dockerfile on the digest it builds `FROM`. Each `rig build` therefore rebuilt the messages
  overlay and every service image above an unchanged base, gave them new layers, and rewrote
  their digests in `rig.lock`, with nothing changed.
- After a publication is verified, Rig now compares its architecture members with the build
  catalog as it stood before the build. When an earlier publication of the same repository has
  exactly those members and its index is still in the registry, Rig points the tag back at that
  index and keeps its digest for the catalog and for dependents. The build output marks such
  images `unchanged` and counts them in its last line. A new tag of unchanged content resolves
  to the same index.
- Adopted catalog rows are never reused. If the earlier index cannot be confirmed or the tag
  cannot be pointed back, the fresh publication stands and the build continues as before.
- The build reference now says that BuildKit deletes the cache mounts a `--no-cache` build
  uses, and that a build command should not change a build argument for a clean build: the
  next ordinary build would not reuse what the clean build produced.

### Compatibility and upgrade

Only the Rig CLI changes. No base image, messages overlay, service image or rig-infra release
has to be rebuilt, and service build commands need no change. Catalog rows written by v0.2.61
or later already record the architecture members, so the first build after upgrading can keep
digests. A row without them is published as before.

The kept index carries the attestation of the build that first published it. The index of the
build that changed nothing stays in the registry untagged until the registry collects it. When
a registry has already collected the earlier index, the fresh publication is recorded instead.

A `--no-cache` build still publishes new digests wherever its steps are not reproducible. The
ordinary build after it keeps them.

### Validation

All 97 local test modules completed successfully: 1,439 passing cases and 2 explicit
native-Docker skips. Two new cases cover an unchanged publication keeping its digest for the
catalog and for dependents, and the conditions under which an earlier index is not reused. The
release workflow runs the Linux sandbox and native replay checks before publishing packages.

Measured on a deployment of zenoh-router, ros2-bag-logger and one Ouster lidar (base image,
messages overlay and driver image) on amd64 with Docker Engine 29.9.2, BuildKit 0.34 and a local
registry: a `rig build` with nothing changed took 434 seconds with v0.2.81 and 5 seconds with
this change, and all three images kept their digests. After a `--no-cache` build, the next two
ordinary builds took 4.9 and 4.7 seconds and published the clean build's three digests
unchanged. arm64, emulated and multi-architecture builds were not measured.

`rig replay prepare` now acquires the runtime images selected by the replay recipe before
running image-dependent preparation helpers. A cold replay host can prepare its selected
player, camera variants, and consumers without manually pulling each image first.

- `--pull missing` is the default: reuse valid local images and acquire missing native images.
- `--pull always` refreshes each selected source once per preparation, including when repair
  or recorded-call inspection causes the plan to be rebuilt.
- `--pull never` requires the selected images to be available locally.
- `replay check` and every dry-run form remain read-only, including with `--pull always`.
  They report proposed pulls without downloading images or writing prepared state.
- Preparation starts no deployment services. Metadata repair and recorded-call inspection
  can run their existing bounded helper containers after the required images are verified.
- Preparation verifies immutable image identities and launcher requirements across replans.
  A failed acquisition or later verification failure preserves the recipe's previous prepared
  binding and restores temporary player wiring.
- Offline replay bundles retain their local-only image requirements.

### Upgrade

Only the Rig CLI changes; no rig-infra release or service image rebuild is required. Update
Rig to v0.2.83, and rebake deployments that need the new behavior in their bundled `./rig`.
Updating a separate Rig installation does not update an existing deployment artifact.

```sh
./rig replay prepare "$RUN" --recipe replay/analysis.yaml
./rig replay prepare "$RUN" --recipe replay/analysis.yaml --pull always
./rig replay prepare "$RUN" --recipe replay/analysis.yaml --pull never
```

### Validation

All 97 local test modules pass: 1,453 passing cases and two opt-in native-Docker skips.
The targeted replay, runtime-image, preparation, recorded-call, session, simulation, and CLI
suites cover 188 cases. Coverage includes cold and warm caches, all pull policies, read-only
checks and dry runs, metadata repair, image and config changes during preparation, and
rollback after failures. The release workflow also requires the full Linux test suite and
native AMD64/ARM64 image acquisition and coordinated replay checks before publishing packages.

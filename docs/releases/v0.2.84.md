The requirements for a Rig-compliant service now live in one document, with a guide for
converting existing software, and `rig certify` closes three gaps that let a non-compliant
service pass.

### Documentation

- The [service contract](https://github.com/christomaszewski/rig/blob/v0.2.84/docs/SERVICE_CONTRACT.md)
  states every requirement as a numbered MUST or SHOULD and says what checks it: a certify
  check, `rig doctor`, a load error, or nothing. It covers the launcher, instance config,
  identity, environment, images, data and health, a full `rigging.yaml` reference, and one
  section for each optional capability. It includes the rules for operational states,
  simulated time, service introspection and message packages, which the README used to
  reference outside this repository.
- The [rigification guide](https://github.com/christomaszewski/rig/blob/v0.2.84/docs/RIGIFICATION.md)
  takes one example service from a plain Compose file to compliant in 14 steps. It maps each
  certify message to its cause and fix, and lists what to check by hand.

### Certify

- New `fixed-names` check. A `container_name` that stays the same when the instance is
  renamed is an error: container names are global to the host, so a second instance cannot
  start. A fixed `name:` on a network or volume that is not `external: true` is a warning.
  Names Compose derives from the project are not reported.
- New `build-images` check. It warns when the rendered Compose pulls none of the declared
  `build.images`, and lists what is pulled instead. It notes, without a warning, the declared
  images that the checked config does not select. It counts every platform of a build matrix.
- `registry` fails a declared build image pulled from another registry or under an extra
  namespace, such as `ghcr.io/acme/widget` for a declared `widget`. This was the "upstream
  image" warning before.
- `tag` reports a pass only when the output pulls at least one declared build image.
- `ros-env` fails a hard-coded `ROS_DOMAIN_ID` or `RMW_IMPLEMENTATION` whether or not the
  service declares `ros_distro`. The warning for a missing value still applies only to
  services that declare it.

### Upgrade

Only the Rig CLI changes; no rig-infra release or service image rebuild is required.

A service that passed `rig certify` only because of these gaps now fails. A CI job that runs
certify from Rig's `main` branch picks the checks up at once. Certify each service before
relying on its gate:

```sh
rig certify --repo . --require-build-check
```

Remove a fixed `container_name`, reference each built image as
`<RIG_IMAGE_REGISTRY>/<image>:<RIG_IMAGE_TAG>`, and pass the ROS settings through from the
environment. The guide's [certify step](https://github.com/christomaszewski/rig/blob/v0.2.84/docs/RIGIFICATION.md#7-certify)
lists each message with its fix.

### Validation

All 97 local test modules pass. `tests/test_certify.py` has 43 cases, 13 of them new; 11 of
the new cases fail on v0.2.83 and the other two guard against over-reporting. Certify was run
before and after on 15 existing services with no new error or warning. Nine variants of the
guide's example service, each broken in one way, give the expected result through real
`docker compose config` output. The release workflow also requires the full Linux test suite
before publishing packages.

See [verification](https://github.com/christomaszewski/rig/blob/v0.2.84/docs/SERVICE_CONTRACT.md#20-verification).

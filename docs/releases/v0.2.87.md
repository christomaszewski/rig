This release fixes the ten most serious findings of a full review of v0.2.86: places where
input from another machine could reach outside the directory it was meant for, checks that
reported "nothing there" when they could not tell, typos in `vehicle.yaml` and `rigging.yaml`
that changed what a vehicle runs without a word, and state files that an interrupted write
could leave empty. rig is now licensed under Apache-2.0.

Several fixes make rig refuse something it used to accept. Read [Upgrade](#upgrade) before
deploying.

### Input from elsewhere

- **Git URLs.** A repository URL reaches `git fetch` and `git clone` from a registry service
  manifest (`source.repo`), a rigging.yaml (`build.sources`, `msgs.source`), `rig.lock`, or
  the `.gitmodules` of any repository rig mirrors. A value beginning with `-` was read by git
  as an option. It is now refused by name before git runs, every fetch and clone passes `--`
  before the URL, and `rig registry validate` reports such a `source.repo`.
- **Registry package paths.** `config.payload` was joined onto the package directory as
  written, so `../…`, or a payload committed as a symlink, made an install copy a file from
  outside the package into `config/` and `config/.pins/`. Every path a package manifest names
  must now stay inside its package directory, symlinks resolved, for install, overlay apply,
  `pkg upgrade`, yank, repin, promote, rebase, save and the validator.
- **Suite plan rows.** A vehicle plan's row names name the files an install writes. A row
  named with `../` could be written outside the deployment and was left there by the
  rollback. Row names are checked against the instance-name grammar before anything is
  written.
- **`rig reconstruct`.** A captured tree holding a symlink that leads outside it is refused:
  after the tree was moved to `--into`, the config overlay could write through such a link.
- **`rig fleet sync`.** A run id reported by a vehicle must be one plain directory name, and
  the destination must resolve inside `--into`. An absolute or `../` id used to place the
  vehicle's files anywhere on the ground station.

### Status

- `rig status` shows `unknown`, never `down`, for a stack whose state could not be read: the
  Docker daemon unreachable, its socket not readable, or launcher output that is not
  `docker compose ps` output. It prints the launcher's last error line and exits 1. The JSON
  form gains an `error` key per stack, null unless the state is `unknown`.
- `rig fleet status` shows `N/M up, K unknown` for such a vehicle.
- `rig cleanup` refuses, and removes nothing, when `docker ps` fails. It used to read a
  failed call as "no containers left".

### Configuration files

- `vehicle.yaml`: an unknown key at the top level, in a row, or under `ros:` or `images:` is
  an error that names the nearest known key (`enable` → `enabled`, `sensor` → `sensors`).
  `enabled` and `run_capture` must be true or false, `order` an integer. A wrong structure
  (`sensors:` as a mapping, `ros:` as a string) is an error instead of a traceback. `rig down`,
  `status`, `logs` and `run end` only warn, so a typo never stops a vehicle from being
  stopped. A top-level key starting with `x-` is ignored.
- `rigging.yaml`: `mirror`, `external_volumes`, `host_ports`, `launch_surface`, `build.images`
  and `build.platforms` must be lists. A bare string was taken apart character by character:
  `rig build` planned `docker pull e`, `docker pull c`, and `rig down --purge` ran
  `docker volume rm d`. Each `verbs` value must be a string, and an `external_volumes`
  pattern may hold `{name}` as its only placeholder.
- A `rigging.yaml` key rig does not read, at the top level or under `build:` or `images:`, is
  reported by `rig doctor` and by `rig certify` (check `descriptor`) as a warning.

### Bake and certify

- `rig certify` fails `discipline` for a Compose service that names no `image:`, as contract
  O2 always said it would. `rig bake` refuses such a service: it used to strip `build:` and
  ship a service with neither.

### State files

- Run manifests, `rig.lock`, the machine identity file (`/etc/rig/vehicle.local.yaml`),
  `registries.yaml`, the user config and the catalog roots are written to a temporary file
  and renamed into place. A power cut or an interrupt during a write leaves the previous file,
  never an empty one.
- Exporting a run that is itself an export no longer rewrites the source's provenance: the
  new export's `.rig/export.yaml` shared the source's file through a hard link.
- `rig fleet up` pushes the roster under a temporary name and renames it on the vehicle, so a
  link that drops mid-transfer leaves the roster the vehicle already holds.

### Fleet and data directories

- `rig down` accepts `--force`, which `rig fleet down --force` forwards: with `--end-run` it
  seals although stacks are still running, as `rig run end --force` does. Every vehicle used
  to reject the flag.
- `rig setup --data-dir NEW --migrate` and `rig provision --data-dir NEW --migrate` refuse,
  before copying anything, an old data directory that is a mount point or a symlink. On a
  mount point the old registry used to be emptied and the command then crashed without
  repointing the setting. Use `--keep-old` there.

### Documentation

- `docs/HOST_SETUP.md` said `./run.sh up` prefers rig and applies an edit made on the
  vehicle. It runs the frozen compose scripts; after an edit, run `./rig up`.
- Both example recipes, and the offline Isaac walkthrough, now select the deployment's Zenoh
  router, without which `rig replay` refuses the session, and describe the simulator's own
  router beside it. The walkthrough's two-router arrangement follows SIMULATION.md's record
  of live use with an external simulator; it has not been run with Isaac.
- The service contract (O9 and the descriptor reference) and `docs/RIGIFICATION.md` describe
  the new checks.

### Upgrade

Only the Rig CLI changes; no rig-infra release or service image rebuild is required. These
changes can make something that worked before stop with a message:

- `rig up` refuses a `vehicle.yaml` with an unknown key or a wrong type. Run `rig doctor` after
  upgrading and fix what it names.
- A service whose `rigging.yaml` gives a bare string where a list is required, or a `verbs`
  value that is not a string, fails to load until it is corrected.
- `rig certify` fails, and `rig bake` refuses, a Compose service with no `image:`.
- Scripts reading `rig status` see exit status 1 and the state `unknown` when Docker cannot be
  reached, and `rig fleet status` counts such a vehicle as a problem.
- `rig fleet down --force` works only on vehicles running this version; an older `rig down`
  reports an argument error.
- Building from source needs setuptools 77 or later. pip fetches it into the build
  environment by itself; an offline build without build isolation needs it installed.

### Validation

All 107 local test modules pass on Python 3.13 and on Python 3.9, the declared minimum. Two
are new, `tests/test_atomic_write.py` (5 cases) and `tests/test_examples.py` (2), and 25
cases were added to existing modules. Every new case fails against v0.2.86's code (the
example checks against v0.2.86's example recipes). Four existing cases changed with the
behaviour they describe: the status rollup, the JSON key set in `tests/test_status.py` and
`tests/test_states.py`, and the roster push whose copy delivers nothing, which the ground
station now catches before starting the vehicle.

No Docker daemon, ROS graph or remote vehicle was available. Status, cleanup, the roster push
and fleet sync were exercised against stand-in `docker`, `ssh` and `scp` commands; the
mount-point refusal against a stubbed mount check. The wheel, sdist and deb were built and
their licence metadata inspected. The release workflow also requires the full Linux test suite
and the coordinated replay job before publishing packages.

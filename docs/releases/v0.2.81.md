Repeated replay can reuse verified file hashes, and sensor-time bag proxies now account for
the transforms that consumers need before processing clouds and other sensor messages.

- `rig replay --recipe analysis --fast` reuses hashes from earlier replay/prepare invocations
  when the resolved path, device, inode, size, and nanosecond modification/change timestamps
  still match. Missing, changed, or invalid cache entries are hashed normally. Full byte
  verification remains the default; all modes reuse hashes within one invocation to avoid
  rescanning the same original and proxy files at each startup phase.
- The cache is local to the deployment and host boot. Recipe/configuration, inventory,
  manifest, expected checksum, runtime-image, host, and startup checks still run. Inputs are
  rechecked before launch and after run capture. Check and dry-run can read the cache without
  writing it. Reports retain hash/cache counts. Fast mode is not a fresh integrity scan and
  cannot detect corruption that leaves every cached filesystem identity field unchanged.
- Sensor profiles accept `tf_lead_time_ms` (default 100 ms) with the rig-infra v1.20.1 player.
  Dynamic TF uses nested transform stamps with a bounded lead; constant static TF is preloaded,
  and window restoration retains every static child frame. Serialized sensor payloads and
  their internal timestamps remain unchanged. See the timing contract for delivery and
  interpolation limits.
- The documentation and CLI help now explain one-recipe workflows, exact instance selection,
  multiple bag loggers, per-camera proxies and ROS image authority, profile selection,
  build/bake/pull scopes, source-run compatibility, and current-deployment image selection.

### Compatibility and upgrade

`--fast` requires only the updated Rig CLI and works with existing compatible proxies. A normal
prepare/replay seeds the hash cache; a cold cache or host reboot still requires full hashing.
It does not remove image pulls, run capture, camera timestamp parsing, or the legacy 20-second
startup delay. Use `--start-delay 0` separately when that settling interval is unnecessary.

The sensor-time TF fixes require Rig **v0.2.81** and the rig-infra **v1.20.1** player bundle with
a compatible native ROS image. Upgrade the deployment's player provider explicitly; installing
Rig elsewhere or preparing a run does not replace an existing vendored player. Source releases
do not rebuild deployment-specific images or baked artifacts.

Existing proxies are immutable. Re-export a sensor profile to obtain revision 2, then prepare
its recipe again. Recipes pinned to an exact proxy ID must select the new export ID. Original
bags and earlier proxy generations remain unchanged.

Deduplication policy is unchanged: conservative mode retains ambiguous byte-identical ordinary
sensor messages, including SBG messages and clouds. Aggressive mode explicitly permits likely
matches across recordings within its receive-time window; it may remove legitimate repeats.
Original-bag playback still performs no live deduplication.

### Validation

All 97 local test modules completed successfully: 1,430 passing cases and 9 explicit
sandbox/native-Docker skips. The release workflow runs the Linux sandbox and native replay
checks before publishing packages.

Regression coverage includes full versus cached verification, unchanged payloads remaining
unopened during fast startup, cache fallback, read-only checks, changed original/proxy files,
and fresh manifest/configuration/image/host validation. Native ROS acceptance covers TF lookup,
static restoration, point-cloud payload preservation, and sensor scheduling; physical-vehicle
and application-specific feature-detection acceptance are not implied.
The companion rig-infra changes passed 261 pure tests and all 21 native ARM64 acceptance tests
without skips. The release workflow additionally gates publication on native amd64/arm64 replay
acceptance; its results are recorded in GitHub Actions.

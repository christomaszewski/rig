Services with the same tier and order now start and stop concurrently, reducing stack startup
time when independent launchers wait for sensor state.

- **`rig up` starts equal-order peers together.** Groups retain the infra → sensors → autonomy
  sequence and ascending order within each tier. Every launcher in a group finishes before
  the next group starts. No `--jobs` flag is required; distinct orders retain serial execution.
- **`rig down` reverses the groups and stops peers together.** Log capture still precedes
  teardown, volume purging follows all teardown groups, and a failed teardown leaves the run
  open. Repeated explicit instance names launch only once for either verb.
- **Newly baked artifacts carry the same scheduling.** The bundled Rig, `run.sh` bootstrap,
  and generated `up.sh`/`down.sh` preserve tier/order barriers and offline image guards.
  Re-bake existing deployments to get the new bundled code and scripts.
- **Output and cancellation remain attributable.** Native launcher output is labeled by
  instance, summaries retain manifest order, and cancellation stops and reaps in-flight
  launcher/Compose descendants. Dry runs show the groups without launching services.

Native deployment commands continue later groups after ordinary launcher failures and report
all failures. Generated baked startup scripts retain fail-fast behavior after draining the
failed group; generated teardown scripts continue later groups and return a failure status.
Group completion follows each launcher's existing contract, not a new readiness probe.
Saved replay/simulation sessions and other verbs retain their existing lifecycle semantics.

The [Windows replay plan](https://github.com/christomaszewski/rig/blob/v0.2.78/docs/windows-replay-plan.md)
records tentative future work for Docker Desktop Hyper-V and offline baked bundles.
Windows support is not implemented in this release.

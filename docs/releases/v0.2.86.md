A value that must differ on every vehicle can now live in the fleet roster, where `rig fleet`
refuses a duplicate, and a vehicle's provisioned values can be exported and applied to its
replacement. Every run records which tier supplied each value and keeps the machine file.
A `rig sim` probe no longer loses its result to the middleware, and an attach that fails says
what went wrong and is not listed as a recording. `rig run diff` says what differs between two
runs' records. An open run names the deployment directory it was last brought up from.

### Fleet roster

- Roster rows take a `vars:` mapping, with the same lowercase names as `rig provision --var`.
  A vehicle finds its own row in the pushed `fleet.yaml` by `id` and reads those values above
  the fleet-level `vars:`. Both are the fleet tier: the machine file still outranks them, and
  a reboot renders them with no ground station. Row values are not forwarded as `RIG_VAR_*`.
- A row with no value for a variable the deployment references does not come up. There is no
  default.
- New top-level `unique:`, a list of variable names. `rig fleet` refuses a roster in which two
  vehicles would hold one value for a listed name, and names the variable, the value and the
  vehicles. The check covers the whole roster on every `rig fleet` verb, also when the verb
  names a subset, and applies `fleet up --var` to the selected vehicles first. A listed name
  that no row sets is refused as a typo. Rig does not know what the value means, only that it
  must differ.
- **Duplicate ids are now an error.** A roster with two rows of one `id` used to load: the two
  vehicles shared a ROS domain and each dropped the other from `fleet_peer_ids`. Such a roster
  must be corrected before any `rig fleet` verb runs. A vehicle also refuses a pushed roster
  that holds its own id twice.
- `rig fleet up` does not start a vehicle the roster did not reach when rows carry values: it
  would come up on the roster it already holds. A roster without row values keeps the earlier
  behaviour, a warning and a normal start.
- Before it pushes a roster with per-vehicle values, `rig fleet up` asks each vehicle for its
  rig version. A vehicle on a rig older than v0.2.86, or one that does not say, is neither
  sent the roster nor started, and the ground station says to re-bake it. An older rig
  refuses every verb, `down` included, once its deployment holds a roster with `unique:`.
- `rig down`, `rig status`, `rig logs` and `rig run end` keep working on a vehicle whose
  configs no longer render, as when a roster value it used has been moved to another vehicle
  while it was up. They use the configs its last `up` rendered and say so, and an `env:` value
  that can no longer be resolved is reported and left out. `rig up` still refuses, and names
  the stacks an earlier `up` left running. Rig does not stop them: bring a vehicle down before
  moving its value.
- New `rig up --roster SHA256`: the vehicle refuses to start unless the `fleet.yaml` in its
  deployment root has that sha256. `rig fleet up` passes the digest of the roster it checked
  when rows carry values, so a push that reported success and delivered nothing, or a file
  edited between the check and the push, stops that vehicle. `--force` does not pass it.
  `--dry-run` pushes nothing and sends no digest.
- When rows carry values, `rig fleet list` shows them in a `VARS` column, and a `ROSTER` column
  says whether each vehicle holds the current roster, an older one or none.

### Stale values

- A value that a vehicle's roster row sets and its machine file, or the tree-local
  `vehicle.local.yaml`, sets differently is a preflight error on that vehicle. `rig up` stops
  and names both tiers and both values; `--force` passes it. An earlier
  `rig provision --var` would otherwise outrank the roster without notice. The same value in
  both places is not an error.
- The same override from the shell (`RIG_VAR_<name>`) does not block. `rig up` prints a note,
  `rig doctor` shows a warning, and `rig fleet up --var` says which row values it overrides.

### Value sources

- Each resolved variable records the tier that supplied it: `vehicle.yaml`, `fleet.yaml`,
  `fleet.yaml row <name>`, the machine file's path, `vehicle.local.yaml`, `shell` or
  `derived`. `rig doctor` lists the values by tier. Bare `rig provision` in a deployment names
  the tier of each value the deployment references.
- A run snapshot's `vars.yaml` carries the same under a new `sources` key.
- A run snapshot keeps the machine identity file, byte for byte, as `machine.local.yaml` when
  the machine has one. Its `env:` values may be sensitive. They were already recorded,
  resolved, in `vars.yaml`, so the copy exposes nothing new.

### Provisioning records

- `rig provision --export [FILE]` writes this machine's file as a record, on standard output
  unless a file is named. It needs no sudo. `values` holds the file's `vars` and `env`, what a
  replacement vehicle may adopt. `machine` holds every other key. Nothing is dropped.
- `sudo rig provision --apply SOURCE` merges a record's `vars` and `env` into this machine's
  file, as `--var` does, and prints each key's old and new value. `--only` and `--except` take
  comma-separated names; a name the record does not hold is an error. `--dry-run` prints and
  writes nothing, and needs no root.
- `--with-identity` also applies the `machine` block. It is for a replaced computer, not for a
  spare that runs beside the original. A changed `vehicle` or `vehicle_id` still needs
  `--force`.
- `SOURCE` may be a run: a run directory, or inside a deployment a run id or label. A run
  stands for the machine file its last `up` captured, so a vehicle that cannot be reached is
  read from a run already harvested to the ground station.
- Rig does not record which values are a vehicle's role and which belong to its airframe. A
  default apply moves all of them: use `--only` or `--except`, and read the printed changes.

### Simulation

A second simulator (Gazebo) and a second host (a Jetson Orin) attached with v0.2.85 unchanged.
These are the fixes they asked for. They apply to Isaac sessions too; an Isaac session that
starts and stops normally prints and writes what it did.

- **The probe's result survives the middleware.** Against Gazebo about one attach in sixty
  failed with "ROS probe failed: Expecting value: line 1 column 1 (char 0)", for two reasons.
  `rmw_zenoh`'s Zenoh writes its own log to standard output, so one warning or error line
  ahead of the probe's JSON made the output unreadable. And the probe left the ROS graph
  before it printed: when closing its Zenoh session ran into Zenoh's ten-second timeout, the
  error replaced the observation, and Rig rolled back a session whose graph the probe had
  found ready. The probe now keeps standard output for its result alone, reports as soon as
  it has observed, and only then leaves; a failed or slow departure is noted and changes
  nothing. A probe that has reported and does not exit is stopped, and its result is used.
- **A probe that fails says what happened.** The message gives how it ended (exit code,
  signal, or stopped at the time limit), how long it ran, what it printed if that was not a
  result, and the last lines of its error stream. The advice to set `simulation.probe` is
  given only when the probe could not be run. A probe that is not ready is followed by what
  the middleware logged. When the launch gate or the check after startup returns no result,
  both streams are kept as `.rig/simulation/probe-failed.json`.
- **A failed attach is listed as `failed`.** `rig sim up` opens the run before it starts the
  services, so a startup that fails leaves a run, and it used to be listed as `sealed` under
  the label that was asked for. Its manifest now carries `failed: {stage, at, error}`.
  `rig runs` and `rig catalog` list it as `failed`, `rig runs` prints the reason, and
  `rig catalog --state failed` finds such runs. `ended:` keeps its meaning.
- **`rig graph` places the simulator.** In an attached run, nodes outside every instance
  namespace that are on the simulator's declared topics, or publish `/clock`, are listed
  under the simulator the run names, worded as the recipe's statement and not verified. In a
  replay, rosbag2's player node is listed with the player instance. Rig's own probe node,
  which the logger can record during startup, is listed as Rig's.
- **Messages name the remedy.** An image the build catalog does not cover is reported as a
  runtime image, with `rig image adopt <image>:<tag>`. Images that are not on the host are
  reported with the `docker pull` for each and the note that `rig sim up` pulls them and
  `rig sim check` never does. A paused external simulator is told to resume, not to start
  and publish `/clock`.
- [An external simulator](https://github.com/christomaszewski/rig/blob/v0.2.86/docs/SIMULATION.md#an-external-simulator)
  gains two arrangements: the simulator on another host, where the probe must join the
  simulator's Zenoh router as a client, and a second deployment on a host where port 7447 is
  taken, which today needs a base image with `rmw_zenoh`'s default router address moved.

### Runs and builds

- New `rig run diff A B`: what differs between two runs' records. It reads each run's
  `manifest.yaml`, the config snapshot of its last `up` (`vehicle.yaml`, `vars.yaml` with each
  value's source, the machine file, `rig.lock` packages and images, the rendered configs) and
  `.rig/images.yaml`, and writes nothing. It lists what differs by section and key, and which
  sections are the same. `A` and `B` are run directories anywhere, or run ids or labels inside
  a deployment. The exit status follows `diff`: 0 no difference of substance, 1 a difference,
  2 trouble. `--json` prints the same report as data.
- `rig run diff` compares images by the per-architecture digests in the captured `rig.lock`.
  A multi-architecture index digest is new on every build, because it carries a build
  attestation, so the same image built twice has two. That is reported as "index digest only"
  and does not count as a difference. An image with no per-architecture record counts as
  changed. The run id, label, times, snapshot name, capture hash and session fingerprint
  differ for any two runs, as do a replay's startup timings: they are listed apart and do not
  count. A `simulation` or `replay` block that only one of the two runs holds is reported in
  one line. Recorded data, logs and probes are not compared.
- An open run names the deployment directory it was last brought up from. Deployment
  directories on one machine share the run registry, so a run left open in one, with its
  stacks back up after a restart, is met from another. `rig status` ends its run line with
  the directory, `rig runs` adds a note under the table, an `up` that joins the run says so,
  and the `rig down` warning for an instance this `vehicle.yaml` does not declare says where
  it was launched. All four speak only when the directory is not this one.
  `rig catalog --state open` says it for every open run it lists, from any directory, and
  `rig catalog --json` carries `up_from` for every run. The directory is read from the run's
  `ups:` entries; nothing new is recorded.
- `rig run end`, `rig run new`, `rig up --run` and `rig down --end-run` refuse to seal the
  open run while a stack it launched is still running and is not one this `vehicle.yaml`
  declares, because `rig down` here cannot stop it. The refusal names the directory whose
  `rig down --end-run` does. This used to seal the run, remove `current` and leave the stack
  running. `--force` seals as before, and a run from another directory with nothing of it
  running is sealed as before. In the run's own directory the same check covers a row taken
  out of `vehicle.yaml` while its stack was up.
- `rig run rm` removes a run whole or not at all. A run that holds files the user cannot
  remove (the stock bag logger writes its bags as root) is refused before anything is
  deleted, with the `chown` that hands it over. It used to stop part-way with a traceback
  and leave the run listed as `interrupted`.
- Every Rig home on one Docker engine shares one managed Buildx builder. The builder now
  carries a digest of its settings (`env.RIG_BUILDER_SETTINGS`), so a home that has never
  used it no longer removes and re-creates it under a build running from another home. A
  real change of settings is seen by every home.

### Upgrade

Only the Rig CLI changes; no rig-infra release or service image rebuild is required. Rosters
without `vars:` or `unique:` load and render as before, apart from the duplicate-id check.

- A vehicle reads its roster row with its own rig, and a baked artifact bundles one. Re-bake
  and redeploy before putting values in roster rows. `rig fleet up` neither sends such a
  roster to a vehicle on an earlier rig nor starts it. Booting on its own with a roster that
  has row values and no `unique:`, an earlier rig ignores them and comes up on whatever its
  other tiers supply; with `unique:` it refuses every verb until that `fleet.yaml` is removed.
  So list every per-vehicle name under `unique:`, and re-bake first.
- To move a value from one vehicle to another, bring the first vehicle down, edit the roster,
  then `rig fleet up`. A vehicle that is still up when its value moves keeps running on it
  until it is brought down.
- A vehicle keeps the last roster that reached it. After a value moves from one row to
  another, the vehicle it moved from must receive the new roster before it runs again;
  `rig fleet up` delivers it to the vehicles it names, and `rig fleet list` shows who holds an
  older one.
- `rig fleet up --dry-run` pushes nothing, so it previews with the roster each vehicle already
  holds.
- Snapshots written by earlier versions hold no `sources` and no machine file. They still
  verify and reconstruct. `rig provision --apply` refuses such a run and says why. A run last
  brought up by an earlier version is not marked `config_dirty_at_seal` by the upgrade.
- A change to the machine file after a run's last `up` now marks the run
  `config_dirty_at_seal` when it is sealed.
- `rig down --end-run` in a directory other than the one a run was brought up from now exits
  1 with the run left open when that run's stacks are still running and this directory does
  not declare them. Run it in the directory the message names, or seal with
  `rig run end --force`.
- Simulation recipes need no change. Scripts that read the `STATE` column of `rig runs` will
  see `failed` for a run whose startup failed under this version; earlier runs keep `sealed`.
- A managed Buildx builder created by an earlier version gains its mark the first time it is
  re-created.

```sh
rig fleet list                               # row values and who holds the current roster
rig provision --export uav-03.yaml
sudo rig provision --apply uav-03.yaml --only altitude_band --dry-run
```

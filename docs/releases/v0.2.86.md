A value that must differ on every vehicle can now live in the fleet roster, where `rig fleet`
refuses a duplicate, and a vehicle's provisioned values can be exported and applied to its
replacement. Every run records which tier supplied each value and keeps the machine file.

### Fleet roster

- Roster rows take a `vars:` mapping, with the same lowercase names as `rig provision --var`.
  A vehicle finds its own row in the pushed `fleet.yaml` by `id` and reads those values above
  the fleet-level `vars:`. Both are the fleet tier: the machine file still outranks them, and
  a reboot renders them with no ground station. Row values are not forwarded as `RIG_VAR_*`.
- A row with no value for a variable the deployment references does not come up. There is no
  default.
- New top-level `unique:`, a list of variable names. `rig fleet` refuses a roster in which two
  vehicles would hold one value for a listed name, and names the variable, the value and the
  vehicles. The check covers the whole roster on every `rig fleet` verb, also when the verb
  names a subset, and applies `fleet up --var` to the selected vehicles first. A listed name
  that no row sets is refused as a typo. Rig does not know what the value means, only that it
  must differ.
- **Duplicate ids are now an error.** A roster with two rows of one `id` used to load: the two
  vehicles shared a ROS domain and each dropped the other from `fleet_peer_ids`. Such a roster
  must be corrected before any `rig fleet` verb runs. A vehicle also refuses a pushed roster
  that holds its own id twice.
- `rig fleet up` does not start a vehicle the roster did not reach when rows carry values: it
  would come up on the roster it already holds. A roster without row values keeps the earlier
  behaviour, a warning and a normal start.
- New `rig up --roster SHA256`: the vehicle refuses to start unless the `fleet.yaml` in its
  deployment root has that sha256. `rig fleet up` passes the digest of the roster it checked
  when rows carry values, so a push that reported success and delivered nothing, or a file
  edited between the check and the push, stops that vehicle. `--force` does not pass it.
  `--dry-run` pushes nothing and sends no digest.
- When rows carry values, `rig fleet list` shows them in a `VARS` column, and a `ROSTER` column
  says whether each vehicle holds the current roster, an older one or none.

### Stale values

- A value that a vehicle's roster row sets and its machine file, or the tree-local
  `vehicle.local.yaml`, sets differently is a preflight error on that vehicle. `rig up` stops
  and names both tiers and both values; `--force` passes it. An earlier
  `rig provision --var` would otherwise outrank the roster without notice. The same value in
  both places is not an error.
- The same override from the shell (`RIG_VAR_<name>`) does not block. `rig up` prints a note,
  `rig doctor` shows a warning, and `rig fleet up --var` says which row values it overrides.

### Value sources

- Each resolved variable records the tier that supplied it: `vehicle.yaml`, `fleet.yaml`,
  `fleet.yaml row <name>`, the machine file's path, `vehicle.local.yaml`, `shell` or
  `derived`. `rig doctor` lists the values by tier. Bare `rig provision` in a deployment names
  the tier of each value the deployment references.
- A run snapshot's `vars.yaml` carries the same under a new `sources` key.
- A run snapshot keeps the machine identity file, byte for byte, as `machine.local.yaml` when
  the machine has one. Its `env:` values may be sensitive. They were already recorded,
  resolved, in `vars.yaml`, so the copy exposes nothing new.

### Provisioning records

- `rig provision --export [FILE]` writes this machine's file as a record, on standard output
  unless a file is named. It needs no sudo. `values` holds the file's `vars` and `env`, what a
  replacement vehicle may adopt. `machine` holds every other key. Nothing is dropped.
- `sudo rig provision --apply SOURCE` merges a record's `vars` and `env` into this machine's
  file, as `--var` does, and prints each key's old and new value. `--only` and `--except` take
  comma-separated names; a name the record does not hold is an error. `--dry-run` prints and
  writes nothing, and needs no root.
- `--with-identity` also applies the `machine` block. It is for a replaced computer, not for a
  spare that runs beside the original. A changed `vehicle` or `vehicle_id` still needs
  `--force`.
- `SOURCE` may be a run: a run directory, or inside a deployment a run id or label. A run
  stands for the machine file its last `up` captured, so a vehicle that cannot be reached is
  read from a run already harvested to the ground station.
- Rig does not record which values are a vehicle's role and which belong to its airframe. A
  default apply moves all of them: use `--only` or `--except`, and read the printed changes.

### Upgrade

Only the Rig CLI changes; no rig-infra release or service image rebuild is required. Rosters
without `vars:` or `unique:` load and render as before, apart from the duplicate-id check.

- A vehicle reads its roster row with its own rig, and a baked artifact bundles one. Re-bake
  and redeploy before putting values in roster rows. Under `rig fleet up` a vehicle on an
  earlier rig does not start: it does not know `up --roster`, and the ground station says what
  the usage error means. Booting on its own, it ignores row values and comes up on whatever
  its other tiers supply, unless the roster has `unique:`, which it refuses. So list every
  per-vehicle name there.
- A vehicle keeps the last roster that reached it. After a value moves from one row to
  another, the vehicle it moved from must receive the new roster before it runs again;
  `rig fleet up` delivers it to the vehicles it names, and `rig fleet list` shows who holds an
  older one.
- `rig fleet up --dry-run` pushes nothing, so it previews with the roster each vehicle already
  holds.
- Snapshots written by earlier versions hold no `sources` and no machine file. They still
  verify and reconstruct. `rig provision --apply` refuses such a run and says why. A run last
  brought up by an earlier version is not marked `config_dirty_at_seal` by the upgrade.
- A change to the machine file after a run's last `up` now marks the run
  `config_dirty_at_seal` when it is sealed.

```sh
rig fleet list                               # row values and who holds the current roster
rig provision --export uav-03.yaml
sudo rig provision --apply uav-03.yaml --only altitude_band --dry-run
```

### Validation

All 100 local test modules pass. None is new; five gain 32 cases between them:
`tests/test_fleet_verbs.py` (12), `tests/test_fleet.py` (9), `tests/test_vars.py` (5),
`tests/test_runs.py` (5) and `tests/test_reconstruct.py` (1). `tests/fixtures/run-v0.2.84/`
holds a run as the v0.2.84 release wrote it: under this version it seals without
`config_dirty_at_seal`, its snapshot still verifies, and `rig reconstruct` overlays it.

The fleet cases run the real `rig up` on local SIL rows; rows with a `host:` go through ssh and
scp shims that run locally. Not exercised: a real vehicle over ssh, a machine file written
under sudo at `/etc/rig`, a baked artifact reading its roster row on a vehicle, and a live
spare swap. Two things were checked once, by hand, against released packages: v0.2.84 read a
roster with row values, ignored them and refused `unique:`; v0.2.85 exited 2 on
`rig up --roster` with "unrecognized arguments". In the suite a stand-in script answers as
v0.2.85 does. The release workflow also requires the full Linux test suite before publishing
packages.
